# Revisión de sesiones — 14 de septiembre de 2026

La revisión identificó renovación indefinida por polling y acceso visual a datos ya cargados cuando no se podía comprobar la sesión. Corregidos en el código local; requieren desplegar servidor y cliente juntos.

1. **Alta — renovación indefinida.** `rolling: true` renovaba ocho horas con cualquier petición, incluidas las verificaciones automáticas. Ahora `server/session-policy.mjs:17` comprueba 30 minutos de inactividad y ocho horas desde el login en cada petición API. `/api/auth/activity` (`server/index.mjs:293`), autenticado y protegido por CSRF, registra actividad explícita; GET y polling no renuevan. La cookie deja de ser persistente y PostgreSQL no amplía su TTL con lecturas.
2. **Alta — interfaz privada sin conexión o con acceso revocado.** La verificación fallida solo mostraba un aviso. `src/useSession.ts:10` desmonta el contenido privado ante desconexión, errores de autenticación, servidor inaccesible y timeout de diez segundos. Comprueba la sesión cada 30 segundos y al recuperar foco, visibilidad o una página del historial. Descarta respuestas anteriores al bloqueo. El cierre bloquea inmediatamente y comunica la revocación entre pestañas; si la red falla, conserva únicamente una marca de cierre pendiente y lo completa antes de admitir otra sesión. Ante una caída que no genera evento de desconexión, la comprobación periódica puede tardar hasta 30 segundos más el timeout de diez segundos en detectarla.
3. **Media — instrucciones persistentes entre usuarios.** Se elimina la copia antigua de `garaje-kaam-prospecting-prompts` (`src/useSession.ts:124`); el historial local pasa a memoria del panel (`src/components/DashboardModal.tsx:687`) y desaparece al desmontarlo. Todas las respuestas API y el HTML de producción envían `Cache-Control` con `no-store` (`server/index.mjs:96`).

Las sesiones anteriores carecen de fecha de inicio y se invalidan en su siguiente petición. No es necesaria una migración de tablas. Un navegador puede restaurar sus cookies al reabrirse: los límites efectivos se aplican en el servidor, independientemente de esa restauración. Los archivos públicos de la interfaz pueden seguir en caché; no conceden acceso a datos API. Datos descargados previamente fuera de la aplicación no pueden retirarse retroactivamente.

Validación reproducible sin base de datos: `npm run test:sessions`, `npm run lint` y `npm run build`. La prueba HTTP usa Express y un almacén en memoria aislado; comprueba cookies, polling, inactividad, límite absoluto, sesiones antiguas y reutilización tras logout. `test:security` conserva su dependencia de una API y base de datos de pruebas; no debe ejecutarse contra una integración que pueda lanzar campañas reales.

Resultados: cuatro pruebas de servidor aprobadas, compilación y lint correctos. En Chromium, con API simulada, se comprobaron desconexión con un panel privado abierto, reconexión, caída del servidor con navegador online, respuesta 401, cierre fallido seguido de recarga, respuesta tardía, limpieza del historial antiguo, pagehide/pageshow, actividad real frente a polling, los dos límites temporales, timeout y cierre entre pestañas. No se ejecutaron comandos de campañas ni pruebas contra PostgreSQL de producción. Opera no se ha probado directamente.
